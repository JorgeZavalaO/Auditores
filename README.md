# Auditores landing

Static, responsive Astro landing for a Peruvian accounting and auditing firm. The Spanish content is based on the supplied company document. The name **Auditores** and its monogram are provisional, not an approved commercial identity.

## Local development

Requires Node.js 22.12 or newer (implemented and verified with Node 24).

```sh
npm install
npm run dev
```

Open the localhost URL printed by Astro. The project builds as static HTML; only the mobile navigation and the demo form use JavaScript. Images are local, responsive WebP files generated by Astro, and Manrope is self-hosted.

```sh
npm run check
npm run build
npm test
npm run preview
```

`npm test` uses the Node built-in runner. It builds isolated preview and production fixtures under `.astro/test-builds/`, checks semantic HTML, working anchor targets, the ten client marks, image and font locality, demo safeguards, and production/preview SEO output. Fixture domains are never accessed or deployed. TDD was explicitly disabled for this implementation; ordinary functional checks remain required.

## Editable content and reusable components

- `src/data/site.ts`: provisional name, legal identity, example contacts, services, client marks, process and FAQ.
- `src/pages/index.astro`: section composition and the primary commercial message.
- `src/components/`: brand, navigation, headings, service cards, demo contact form, icons and footer.
- `src/layouts/BaseLayout.astro`: language, metadata, social image and structured data.
- `src/styles/global.css`: design tokens, layouts and responsive behavior. The primary color is `#0A1267`.
- `config/site.mjs`: shared domain validation and indexing readiness gate.

The original DOCX, reference JPG and `Logo-clientes/` folder remain untouched. Client PNGs are copied into the Astro asset pipeline; they are not recreated. The partners' **20 years of experience** are clearly attributed to the partners, never presented as the firm's age.

## Example contacts and form

The requested example details are `contacto@example.com` and `+51 999 999 999`. They are deliberately shown as plain text and identified as example data. They do not initiate calls, email messages or WhatsApp conversations.

The form is a **local demonstration only**. It performs native browser validation and displays an explicit preview confirmation. It sends no requests, logs no personal information and writes to no storage. It does not show a false “message sent” confirmation. Without JavaScript, submission is disabled and a notice explains the limitation.

Before a real launch, implement and verify an actual form delivery endpoint with server-side validation, spam protection and appropriate privacy information. Do not remove the preview notice or change the button to imply real delivery before that exists. Form delivery is not included in this project.

## SEO strategy

One commercial route avoids unnecessary competing service pages. Each secondary intent has a distinct section on the same page; repeated keywords are not used to manufacture extra pages.

| Intent | Placement |
| --- | --- |
| Auditoría y asesoría contable para MYPES en Perú | Page title, description, opening copy |
| Outsourcing contable y financiero | Services section |
| Auditoría financiera y tributaria | Services section |
| Gestión laboral y planillas | Services section |
| Diagnóstico contable y tributario gratuito | Conversion section and contact |
| Regularización, control interno and ERP | Supporting services |

There is one H1, a semantic heading hierarchy, accessible anchor navigation, descriptive image alternatives, an explicit page language and static source-readable content. Structured data describes actual service categories without fabricated reviews, contacts, locations or credentials. This is a technical and content foundation, not a guarantee of rankings. Any future service page should have a distinct user need, substantial unique content and a non-overlapping target intent.

## Publication checklist

1. Approve and replace the provisional commercial identity and monogram.
2. Replace the example contact details in `src/data/site.ts`; set `contactIsExample` to `false` after replacing the copy. Review the utility bar, contact section and footer to remove preview labels only when appropriate. Contact links are intentionally absent; add them only for verified real channels.
3. Verify client-logo publication permission, the legal company name and the partners' experience claim. No credentials, testimonials or business address were invented.
4. Configure and test real form delivery, then provide the corresponding privacy information.
5. Copy `.env.example` to `.env`; set `SITE_URL` to the real HTTP(S) public origin with no path, credentials, query or fragment. Domain syntax is validated, not ownership or DNS.
6. Set `PUBLIC_LAUNCH_READY=true` **only after the business information and launch checklist are approved**. Supplying a domain alone never enables indexing.
7. Run check, build, tests, desktop/mobile review and the real contact-flow verification. Test the deployed domain and submit its sitemap through the business's search-console account after deployment is authorized.

Default preview output uses `noindex, nofollow`, `robots.txt` with `Disallow: /`, and no canonical, sitemap or business schema. Configured launch output enables indexing, a canonical and social URLs from the same origin, a sitemap and `ProfessionalService` structured data. `robots.txt` is a crawler policy, not an access-control mechanism. The launch flag is a deliberate release decision and does not automatically verify the business facts, contact delivery or domain ownership.

No analytics, remote font calls, tracking cookies or unnecessary cookie banner are included. Deployment, an actual domain, form delivery and search-console integration were not requested or performed.
